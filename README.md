# RIX STORM PANEL 2.5 — Railway One-Service Edition

این نسخه دقیقاً برای اجرای پنل **در همان سرویس Railway** طراحی شده است. صفحهٔ «افزودن سرور»، ساخت نود، Agent خارجی و دستور نصب روی VPS حذف شده‌اند. هستهٔ Xray و Caddy در زمان build داخل Docker image نصب می‌شوند؛ زمان اجرای برنامه Xray را بالا می‌آورد و تنظیمات کاربران را خودکار همگام می‌کند.

## چه چیزی خودکار است؟

- Xray-core و Caddy داخل همان سرویس Railway اجرا می‌شوند؛ دستور جداگانه‌ای روی VPS لازم نیست.
- HTTPS/گواهی عمومی از لبهٔ Railway می‌آید؛ Caddy مسیرهای WebSocket را به Xray داخلی می‌فرستد.
- هنگام ساخت کاربر فقط نام، پروتکل، حجم و تاریخ اعتبار وارد می‌شود.
- پورت عمومی کانفیگ‌ها 443 است؛ مسیر WebSocket براساس پروتکل خودکار انتخاب می‌شود.
- افزودن، غیرفعال‌کردن، فعال‌سازی مجدد و حذف کاربر، پیکربندی Xray داخلی را بازسازی و اعتبارسنجی می‌کند.
- نود داخلی پشت‌صحنه ساخته می‌شود تا دیتابیس نسخه‌های قبلی قابل مهاجرت باشد؛ کاربر دیگر صفحهٔ مدیریت نودها را نمی‌بیند.
- اگر دیتابیس نسخهٔ قبلی داشته باشد، کاربران VLESS، VMess و Trojan به مسیرهای WSS منتقل می‌شوند. حساب‌هایی با پروتکل‌های ناسازگار با ورودی HTTP عمومی Railway غیرفعال می‌شوند تا لینک ظاهریِ کارنکردنی تولید نشود.

## محدودیت واقعی Railway

ورودی دامنهٔ عمومی Railway برای HTTP/HTTPS و WebSocket مناسب است. بنابراین این نسخه فقط این سه روش را در منوی ساخت کاربر فعال می‌کند:

- **VLESS + WebSocket + TLS (WSS)**
- **VMess + WebSocket + TLS (WSS)**
- **Trojan + WebSocket + TLS (WSS)**

این حالت Reality خام، Shadowsocks خام، UDP مستقیم، gRPC یا XHTTP را از طریق دامنهٔ HTTP عمومی Railway ارائه نمی‌کند. این موارد در UI به‌عنوان ویژگیِ آماده پنهان شده‌اند، نه اینکه لینک غیرقابل‌اتکا تولید شود. Railway سرویس TCP Proxy جداگانه هم دارد، اما آن به تنظیم شبکهٔ اضافه و یک پورت TCP مشخص نیاز دارد و به‌تنهایی UDP یا همهٔ پروتکل‌ها را خودکار نمی‌کند؛ این بسته عمداً به آن وابسته نیست تا نصب ساده بماند.

## استقرار روی Railway

1. همهٔ فایل‌های ZIP را در ریشهٔ مخزن GitHub قرار بده؛ پوشهٔ بالادستی اضافه لازم نیست. یک Railway service از repository بساز. فایل `Dockerfile` در ریشه، Xray و Caddy را هنگام build نصب می‌کند.
2. در **Variables** حداقل دو مقدار امن تنظیم کن:
   - `ADMIN_USERNAME`: نام مدیر.
   - `ADMIN_PASSWORD`: رمز یکتا حداقل ۱۶ کاراکتری.
3. اگر از نسخهٔ قبلی `SECRET_KEY` یا `DATA_ENCRYPTION_KEY` تعریف کرده‌ای، همان مقادیر را نگه دار. برای نصب تازه این دو متغیر اختیاری‌اند؛ برنامه آن‌ها را در Volume روی `/data` می‌سازد و نگه می‌دارد.
4. در بخش **Networking → Public Networking** برای سرویس یک Railway domain بساز. اگر از دامنهٔ سفارشی استفاده می‌کنی، `PUBLIC_BASE_URL=https://your-domain.example` را در Variables اضافه کن. مقدار `PORT` را دستی تنظیم نکن؛ Railway آن را می‌دهد.
5. در بخش **Volumes** یک Volume برای همین سرویس با Mount Path برابر `/data` بساز. این کار برای حفظ SQLite، کلیدهای خودکار و کاربران بعد از Deploy مجدد مهم است.
6. Deploy را انجام بده و صفحهٔ اصلی را باز کن. کارت «اطلاعات سرور» دامنه، پورت عمومی 443، پروتکل‌های فعال و وضعیت Xray را نشان می‌دهد. اگر Xray آنلاین نیست، بخش Deploy Logs را بررسی کن.
7. از «کاربران و اشتراک‌ها» کاربر بساز. نیازی به صفحهٔ نود یا اجرای دستور روی سرور دیگر نیست.

### نکات پایدارسازی و امنیت

- قبل از جایگزینی نسخهٔ فعال از Volume/دیتابیس Railway و متغیرهای فعلی نسخهٔ پشتیبان تهیه کن؛ کلید رمزگذاری قدیمی را تغییر نده.
- این برنامه برای **یک replica** طراحی شده است؛ چند replica با پیکربندی محلی Xray و SQLite همگام نیستند.
- بدون Volume روی `/data` دیتابیس و کلیدهای خودکار ممکن است در Deploy بعدی از بین بروند.
- اگر از متغیر `DATA_ENCRYPTION_KEY` در نسخهٔ قدیمی استفاده می‌کردی، حتماً همان مقدار را نگه دار. اگر این کلید عوض شود، اطلاعات حساس ذخیره‌شده با کلید قبلی قابل رمزگشایی نیستند.
- مقدار مصرف ترافیک هنوز از Stats API زنده خوانده نمی‌شود؛ ثبت حجم در این نسخه دستی است. محدودیت انقضا و حجم ثبت‌شده بررسی می‌شود، اما نباید آن را حسابداری لحظه‌ای ترافیک دانست.
- این بسته در محیط محلی تست می‌شود، اما بررسی نهایی اتصال واقعی باید پس از Deploy از سمت شبکه و کلاینت انجام شود؛ موفقیت تست محلی به‌تنهایی اتصال اینترنتی را ثابت نمی‌کند.

## ساختار اصلی (همگی در ریشه)

- `main.py` — پنل، ساب‌پنل و عملیات مدیر
- `railway_xray.py` — مدیریت داخلی Xray و همگام‌سازی کاربران
- `Caddyfile` و `start.sh` — مسیردهی HTTP/WebSocket و اجرای فرایندها
- `protocols.py` — ساخت لینک کانفیگ‌ها
- `models.py`, `database.py`, `security.py` — دیتابیس و رمزگذاری
- `Dockerfile`, `requirements.txt` — ساخت image برای Railway

## تست محلی توسعه

```bash
python -m pip install -r requirements-dev.txt
python -m pytest -q
```

۲۰ تست محلی در حال حاضر قالب‌های رابط، مسیرهای حذف‌شدهٔ VPS، گزینه‌های پروتکل و ساختار کانفیگ Xray را بررسی می‌کنند. این محیط امکان ساخت Docker image و آزمایش اتصال از یک کلاینت واقعی به دامنهٔ Railway را نداشت؛ آن آزمون‌ها باید پس از Deploy انجام شوند.
